# TaskLocal | Customer Booking

Product B — the demand-side (customer) web and mobile application for TaskLocal Home-Service. Renamed to match the "TaskLocal | X" naming already used by Product A ("TaskLocal | Provider workspace") and Product D ("TaskLocal | Trust & Safety"), found during a brand audit across all four products.

**Live demo:** [tasklocal-home-service-customer-app.vercel.app](https://tasklocal-home-service-customer-app.vercel.app) — now running against the team's real, shared Supabase project (see "Current status" below), not local demo mode. Log in with one of the four demo accounts on the login screen, or sign up for a new one — the sign-up path is live and its database migration has been applied (see "Current status" below).

## Overview
**Product B, Customer (demand) Web and Mobile Application for TaskLocal Home-Service** is the demand-side interface for TaskLocal, a two-sided local marketplace connecting independent home-service providers (house cleaning, Handy People services, moving help) with local customers who need that work done. TaskLocal takes a commission on each booking made through the platform.

## Target User
This product is built for **busy local residents booking home services** — for example, a working professional or renter who needs to find, compare, and book a trustworthy provider for a one-off or recurring job (a deep apartment cleaning, a small repair, help moving) without cold-calling or texting multiple providers to compare price and availability.

## Scope decisions

This product is scoped to the New York City metro area only — for currency, for dates and times, and for every other locale-dependent choice in it. `frontend/js/utils.js` formats prices with `Intl.NumberFormat("en-US", { currency: "USD" })` on purpose, not as an oversight.

Multi-language support — the ten citywide languages New York City recognizes (Spanish, Chinese, Russian, Bengali, Haitian Creole, Korean, Arabic, Urdu, French, and Polish) — was requested and reviewed by this product's creator, including what building it would actually require (moving every piece of visible text out of the code and into per-language files, right-to-left layout support for Arabic and Urdu, translation as an ongoing task rather than a one-time one, and coordination with Products A and C so a non-English-speaking customer's journey does not break partway through). Declined for now: at this project's present stage, the scope that would add was judged too large relative to the benefit.

## Role in the Four-Product Suite
Product B is the primary, customer-facing entry point to the marketplace. It lets customers browse vetted provider listings, filter by service type, price, and availability, and securely book services. It works alongside the other three products in the team's suite as follows:

* **Product A (Provider App):** Where independent service providers create listings and manage incoming bookings. [github.com/Joanalbayrak-111/Tasklocal-Provider-App](https://github.com/Joanalbayrak-111/Tasklocal-Provider-App)
* **Product B (Customer App — This Repo):** Where customers discover, schedule, and pay for services.
* **Product C (Matching Chatbot):** Helps customers describe custom jobs in their own words and matches them to relevant provider listings. Repo not yet shared with the team as of this writing.
* **Product D (Trust & Safety Dashboard):** Lets the internal team monitor flagged listings and bookings and maintain quality control across the platform. [github.com/sarahgdykes-ux/TaskLocal-Trust-and-Safety-dashboard](https://github.com/sarahgdykes-ux/TaskLocal-Trust-and-Safety-dashboard)

All four products share a common data schema (customers, listings, providers, bookings, ratings, and safety reports) agreed on by the team, and — as of this round of integration work — a common live Supabase database. See [PRESENTATION.md](PRESENTATION.md) for the cross-product demo narrative and current integration status of all four.

## Architecture

- **Frontend** (`frontend/`): plain HTML/CSS/JavaScript (no build step), deployed on Vercel. Works on both desktop and mobile browsers — it's a responsive site, not two separate codebases. Supports light and dark mode automatically via `prefers-color-scheme`.
- **Backend** (`backend/`): PostgreSQL via Supabase. `backend/schema.sql` defines the tables (matching the team's shared data schema exactly) and Row Level Security policies. `backend/seed_data.sql` loads the team's synthetic dataset. `backend/data/` holds CSV copies of the same data (the team's original format); `frontend/data/` holds JSON copies, used as local mock mode's fallback — see "Run it locally" below.
- Auth is Supabase Auth (email + password). Four fictional demo accounts (Alex Rivera, Jordan Lee, Morgan Reyes, Taylor Chen — not real teammates, deliberately, since this file and `frontend/js/demo-users.js` both ship in a public repo) are seeded via `backend/scripts/seed-demo-users.mjs` so anyone can log in and click through without setting up their own account. `signup.html`/`page-signup.js` also let a real first-time visitor create their own account (`backend/schema.sql`'s `handle_new_customer_signup` trigger provisions the matching `customers`/`customer_profiles` rows) — see the pending-migration note in Known Limitations before relying on this in the live deployment.
- Shared pure logic (HTML-escaping, listing filters, currency formatting via `Intl.NumberFormat`, deciding whether a booking shows a rating form) lives in `frontend/js/utils.js` rather than being copy-pasted per page, and is unit-tested in `frontend/js/utils.test.mjs`. Every page module (`nav.js`, `page-index.js`, `page-login.js`, `page-listing.js`, `page-listings.js`, `page-bookings.js`) has its own DOM-level tests using `jsdom` — the one place `frontend/`'s dependencies go beyond zero. `frontend/js/data-integrity.test.mjs` checks the actual data (frontend/backend mirrors agree, no orphaned foreign keys, no expired "bookable" slots — see "Data quality note" above); `frontend/js/contrast.test.mjs` checks real WCAG contrast ratios computed from `css/styles.css`'s actual color values; `frontend/js/axe.test.mjs` runs `axe-core` against every page's real HTML template for structural accessibility issues (it caught a missing `<main>` landmark on two pages, since fixed).
- Branding: `frontend/assets/logo.svg` — a simple, colorful NYC brownstone mark — is the favicon (with a `favicon-32.png` fallback for browsers that don't support SVG favicons) on every page, and appears in the nav bar and on the login screen. One SVG source; edit it there if the mark ever changes.
- Each page sets light/dark `<meta name="theme-color">` tags (matching `styles.css`'s `--bg` values) so supported mobile browsers tint their own chrome/status bar to match instead of defaulting to white or black.
- `frontend/robots.txt` disallows all crawling — keeps this login-gated synthetic-data app out of search results now that it's deployed to a real, public Vercel URL (see Section 3 below).
- `frontend/manifest.json` (linked from every page) makes the app installable — "Add to Home Screen" / standalone window — with `assets/logo.svg` plus 192×192 and 512×512 PNG fallbacks (Chrome's install criteria specifically want a PNG, not just an SVG marked `sizes="any"`), plus a separate `purpose: "maskable"` icon pair (`logo-maskable.svg` → `icon-maskable-*.png`) scaled down and centered with padding so Android's adaptive-icon mask can't clip the house's roofline.
- `frontend/sw.js`, registered by `frontend/js/register-sw.js` on every page, is what actually makes that installability work reliably and gives the app real offline support (network-first, falling back to the last-cached copy of the app shell) — the manifest/icons alone don't guarantee either without a service worker present. It only handles same-origin GETs, so it never intercepts Supabase auth/RPC calls.
- `vercel.json` sets a strict Content-Security-Policy (`script-src`/`style-src 'self'`, no `'unsafe-inline'` — the app has zero inline `<script>` or `style="..."` left anywhere, on purpose; `connect-src` is `'self' https://*.supabase.co` — same-origin requests plus the Supabase API, nothing else; ES module loading like the `esm.sh` import is a `script-src` concern, not `connect-src`) plus `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and a `Permissions-Policy` disabling camera/mic/geolocation/payment/USB/FLoC. **This only takes effect on an actual Vercel deployment** — it's not read by local demo mode's `python3 -m http.server`. Confirmed live via response headers on the deployed URL above.
- `.github/workflows/test.yml` runs `node --test --experimental-test-coverage frontend/js/*.test.mjs` on every push/PR, after `npm ci` (not `npm install` — fails loudly on any lockfile drift instead of silently installing something slightly different) and `npm audit` (fails the build on any known vulnerability) for both `frontend/` and `backend/` — see Section 4 below. `.github/workflows/live-tests.yml` separately runs the live-database suite (`frontend/js/live/`) on a monthly schedule plus manual dispatch — deliberately not on every push, since it writes real rows to the shared database (see that suite's own header comments).
- `frontend/js/error-reporter.js`, loaded on every page, catches uncaught errors and unhandled promise rejections and keeps the last 20 in `sessionStorage` — readable via `window.TASKLOCAL_ERROR_LOG` in devtools — so a broken session leaves a trace instead of vanishing with the tab.
- `SCHEMA.md` documents every shared table, RPC function, and RLS policy this repo touches on the project shared with Products A/C/D, plus known drift (the `providers` table, the `service_type` display-label mismatch) — proposed from Product B's side, not yet a jointly-adopted cross-repo document.
- **Current status: connected to the team's real, shared Supabase project** (`frontend/js/config.js`), not local demo mode — this changed after the team set up shared infrastructure for integration across Products A/B/C/D. The shared database's `customers`/`listings`/`bookings` tables existed as `Customers`/`Listings`/`Bookings` (capitalized, no keys, no constraints, no RLS policies) before this connected to them — renamed to match, then brought up to match `backend/schema.sql` exactly (keys, constraints, the two Product-B-only tables, all triggers, all RLS policies) via a one-time migration. That migration also found and removed two RLS policies that predated Product B's involvement and let *any unauthenticated visitor* read and rewrite every booking in the shared database (their policy conditions were unconditionally `true`) — confirmed closed by directly testing that an anon key can no longer read or modify a real booking, not just by checking the policy no longer exists. The full login → browse → book → My Bookings flow has been verified end-to-end against this real database, including confirming server-side price computation and status enforcement actually fire (not just that the mock-mode equivalent does). Section 2 below is now largely historical (the setup it describes already happened); Section 1 still describes the fastest way to run this locally without touching the real database.

## Data quality note

The synthetic `bookings.csv` from the team's shared dataset originally referenced 42 `listing_id`s that don't exist in `listings.csv` (the two files look like they were generated in separate runs). `backend/seed_data.sql` only ever contained the 58 bookings whose `customer_id` and `listing_id` both cross-reference real rows — those 42 were dropped before seeding from the start. `backend/data/bookings.csv` itself, though, still had all 100 rows sitting in it as raw/uncurated data until `frontend/js/data-integrity.test.mjs` was written and caught it; trimmed to match `seed_data.sql` exactly, confirmed by exact set equality between "orphaned foreign key" and "missing from `seed_data.sql`" (no partial overlap either way — a clean cut). Worth flagging back to Joan since her `generate.py` is the source of the dataset, in case a future re-run reintroduces the same mismatch.

Two more real data-quality bugs `data-integrity.test.mjs` found and fixed, same session: `backend/data/listings.csv` had corrupted JSON in `availability_slots` for 8 of 55 listings (an unterminated-string escaping bug — every one of the 8 should have been `[]`, per both `frontend/data/listings.json` and `seed_data.sql`, which already agreed with each other). And separately — this one durably re-checked on every test run, not just fixed once — `availability_slots` is static seed data presented to customers as *open, currently-bookable* time slots; "today" keeps moving in a way static data doesn't, so slots quietly age into the past with nothing to notice. Found 15 listings with an already-past "bookable" slot at the time this was caught. `data-integrity.test.mjs` now compares every slot against `Date.now()` at whatever moment the test actually runs, so a slot that's fine today but stale by the next push gets caught then instead of sitting there unnoticed.

## Security

**A note on scope: most of this section describes real Supabase mode.** The live demo linked above runs in **real Supabase mode** (see "Current status" above) — this note used to say otherwise and was stale, corrected after an independent review's own live testing caught the contradiction. Mock mode still exists and still matters: anyone who clones this repo and runs it locally *without* configuring a Supabase project (see "Run it locally" below) gets mock mode automatically, and it has no server at all — every "protection" mock mode has is a client-side convention the app's own UI follows (`frontend/js/api.js` computing `total_cost` itself, the rating form only appearing on completed bookings, etc.), not an enforced boundary. In mock mode, opening the browser console and directly rewriting `localStorage`'s `tasklocal_mock_bookings` key can fabricate a booking, set an arbitrary price, or self-assign a rating — nothing server-side stops that, unlike the RLS policies and triggers described below, which only run in real Supabase mode.

- No secret keys, passwords, or API keys are committed to this repo. `frontend/js/config.js` only ever holds the Supabase **anon** key, which is meant to be public (Supabase enforces access with Row Level Security, not by hiding this key) — see `backend/schema.sql` for the actual policies.
- The Supabase **service role** key (which bypasses RLS) is only ever read from an environment variable in `backend/scripts/seed-demo-users.mjs`, run locally, and is never written to a file that gets committed. `.gitignore` excludes `.env`.
- Row Level Security means a signed-in customer can only read/write their own bookings and profile — not anyone else's.
- All form inputs (login, search/filter, booking, rating) are validated before use so unexpected input can't break the app.
- `total_cost` is never trusted from the client: a booking's price is computed from the listing's real `hourly_rate` by a Postgres trigger (`bookings_set_total_cost` in `backend/schema.sql`) on insert, so a tampered client request can't set an arbitrary price. Mock (local demo) mode mirrors this by computing the total in `frontend/js/api.js` rather than accepting it as a parameter.
- `booking_status` on a new booking is forced to `'pending'` server-side (`bookings_enforce_new_status` trigger) for any authenticated client request, so a customer can't self-insert a booking as already `'completed'`.
- The RLS `UPDATE` policy on `bookings` has a matching `WITH CHECK`, and a trigger (`bookings_protect_update`) additionally rejects any authenticated-client update that touches `customer_id`, `listing_id`, `total_cost`, or `booking_status` — a signed-in customer can only ever change their own booking's `rating`, even via a direct API call that bypasses the app's UI.
- Demo account emails/passwords in `frontend/js/demo-users.js` and `backend/scripts/seed-demo-users.mjs` are deliberately fictional (`@example.com`, RFC 2606-reserved) rather than teammates' real `@pursuit.org` addresses — they used to be real names/emails paired with real passwords for the matching Supabase Auth accounts, which was a genuine exposure once actually noticed (public repo + a real person's email + a written password is a real credential-reuse risk if anyone ever reused that password elsewhere), not just a hypothetical one. `login.html`'s demo-account buttons still look the password up from the in-memory array rather than exposing it via an HTML attribute, so it's at least not sitting in the rendered page source on top of that — but the source file itself is still public, which is exactly why the identities in it need to stay fictional going forward.
- The email/password `<input>`s on `login.html` intentionally have no `name` attribute (the JS reads them by `id`) — with a `name`, a browser falling back to native form submission (JS blocked or failed to load) would leak the password into the URL as a GET query string.
- Creating a booking writes to two tables (`bookings`, then `booking_schedules`). That's done via one Postgres function, `create_booking_with_schedule` (`backend/schema.sql`), called through `supabase.rpc(...)` — not two separate client-side inserts. A function call runs inside a single transaction, so a failure partway through can't leave an orphaned booking with no recorded time slot the way two sequential round-trips could (**atomicity**).
- Separately, that same function is **idempotent** on `booking_id`: if the call already committed once but the client never saw the response (dropped connection, timeout), a retry carrying the same `booking_id`/`customer_id`/`listing_id` returns the existing booking instead of erroring or creating a duplicate. `page-listing.js` generates the `booking_id` once per slot selection and reuses it across a manual "Book" retry so this actually applies. Scope of what that covers: it protects a retry on the *same page load* (click "Book" again after seeing an error). It does **not** survive a page reload or tab crash between the lost response and the retry — `pendingBookingId` lives in a plain JS variable, not persisted storage, so a reload resets it and a subsequent retry gets a fresh id. In the rare case the original call had actually silently succeeded, that specific sequence (lost response → reload → retry) could still produce a duplicate booking.

## Accessibility

Accessibility work on this app is evaluated against ten disability/impairment categories (visual, auditory, motor/physical, cognitive and learning, speech, seizure and physical-reaction disorders, vestibular, mental health, aging-related, and temporary/situational), rather than treating "accessibility" as one undifferentiated pass. A text- and form-based booking app does not have equal surface area in all ten — the notes below say which categories the app actually touches today, what's covered, and what is honestly still open. Automated tools (axe-core, WCAG contrast checkers) verify categories 1–2 well; the rest generally need either real assistive-technology user testing or a deliberate manual walkthrough, so nothing here is called "maximized" on the strength of an automated scan alone.

- **Visual (blindness, low vision, color blindness)** — the axe-core test suite (`frontend/js/axe.test.mjs`) checks every page for WCAG contrast violations and missing alt text/labels on every CI run. Semantic HTML and labelled form controls are used throughout rather than div-soup with click handlers.
- **Auditory (deafness, hard of hearing)** — this is a structural strength, not a bolt-on feature: the app has zero audio or video content anywhere in the product (no notification sounds, no video walkthroughs, no voice prompts), so there is no audio-only information a Deaf or hard-of-hearing user could miss. Every state the app communicates (booking confirmed, slot taken, error) is conveyed in visible text.
- **Motor/physical (limited fine motor control, switch/keyboard-only use)** — all interactive elements are real `<button>`/`<a>`/form controls (not `<div onclick>`), so they are reachable and operable by keyboard and by switch-access software by default; the axe-core suite checks for this structurally. Real per-user testing with keyboard-only or switch-access navigation has not been done.
- **Cognitive and learning (dyslexia, ADHD, autism spectrum, memory impairment)** — form errors and status messages use plain, specific language (see the writing-style note on the booking flow) rather than jargon, and the booking flow is a short, linear sequence rather than a multi-branch wizard. No dedicated readability/plain-language audit has been run against this category specifically.
- **Speech** — not currently applicable: the app has no voice-input or voice-command feature. Revisit this category if one is ever added.
- **Seizure and physical reaction disorders (photosensitive epilepsy)** — not currently applicable: the app has no flashing, strobing, or rapidly-animated content anywhere.
- **Vestibular disorders (motion sensitivity)** — the app has no parallax scrolling and no heavy decorative animation, so there is little surface for this category today; this has not been verified against `prefers-reduced-motion` handling specifically.
- **Mental health conditions (anxiety, PTSD)** — error and warning states use calm, factual wording rather than alarming tone or color; not independently verified with real users.
- **Aging-related impairment** — addressed indirectly, since it is typically several of the above (vision, hearing, motor, cognitive) compounding together rather than a separate design target — the visual-contrast, keyboard-operability, and plain-language work above all carry over.
- **Temporary and situational impairment** (broken arm, screen glare, noisy environment, one-handed use) — carried for free by the same underlying work: real buttons/links support one-handed and assistive-switch use, plain text-based status carries over a noisy environment, and the contrast work helps in bright glare.

**Where categories can genuinely conflict**, and how this app resolves it in practice: Deaf-community needs (plain language, no audio-only content) and blind-community needs (screen reader support, keyboard navigation, contrast) are complementary here, not in tension — the classic tension points (flashing content vs. photosensitive epilepsy, animation vs. vestibular disorders) only arise once video, animation, or flashing content exists, and this app deliberately has none of those. This is not claimed as "accessibility maximized" — it is an honest account of what a text/form-based product with no media surface starts with for free, what automated tooling actively verifies (categories 1–2), and what still needs real assistive-technology user testing before being called complete (categories 3, 4, 7, 8 above).

## Known limitations

- **Fixed and applied live (2026-09-04):** `backend/schema.sql`'s three additive fixes — closing a `total_cost` trust-escape-hatch and a premature-rating gap on the `bookings` triggers (both found by an adversarial review), and a new trigger that provisions a `customers`/`customer_profiles` row the instant a self-service sign-up completes — are committed, tested (`frontend/js/live/rls-policies.test.mjs` for the trigger fixes; the mock-mode signup tests plus a fake-client real-mode suite for sign-up), **and confirmed live against the shared database** (migration: `backend/sql/2026-09-04-signup-and-trigger-hardening.sql`, applied and verified via direct queries against `pg_trigger`/`pg_proc`). Note on scope: this is a training project for a Pursuit capstone, not a production service — sign-up existing and working end-to-end matters more than it being a fully hardened, production-grade flow (see the email-confirmation/rate-limit caveat below, which is a real, accepted Free-tier limitation, not a bug).
- This project's Supabase plan sends real confirmation emails on sign-up (not disabled for this demo), and the Free tier's email-sending rate limit is very low — expect `over_email_send_rate_limit` if more than a couple of real sign-ups happen in a short window. `api.js`'s `signUp()` surfaces this as a specific, actionable message rather than a generic error.
- `backend/schema.sql`'s RLS policies, triggers, and functions have now been exercised against the real, shared Supabase project (see "Current status" above) — no longer an open gap, and no longer just a one-time manual check: `frontend/js/live/rls-policies.test.mjs` and `known-issues.test.mjs` (Tier 2, Section 4 below) turn it into a repeatable, 15-test live suite (split across two files so one deliberately-failing known issue doesn't fail the whole CI job — see Section 4). `frontend/js/api-supabase.test.mjs` still separately covers `api.js`'s real-Supabase-mode application logic (auth, query building, the retry-on-collision logic) against a hand-built fake client, for fast, offline, per-commit coverage that doesn't depend on the real database being reachable — see Section 4 below for the full three-tier test breakdown (roughly 187 tests total).
- **Fixed and applied live (2026-09-04):** the `alex.rivera@example.com` demo account's Supabase Auth user previously carried an `app_metadata.role` of `"safety_team"` — found by `frontend/js/live/rls-policies.test.mjs`'s own tests, not by manual review. Originally documented as one policy (`bookings_safety_team_select`); a follow-up query (`backend/sql/check-safety-team-policy-scope.sql`) found **six** policies across **five** tables keyed to that role, none defined in this repo's own `schema.sql`: `bookings`, `chatbot_requests`, `customers`, and `listings` (SELECT), plus `trust_safety` (SELECT **and** UPDATE). `listings` is already public-read, so no incremental exposure there — but `chatbot_requests` and `customers` were not previously known to be reachable through this account. Almost certainly Product D's Trust & Safety Dashboard's own mechanism for its real reviewer accounts, working as intended for them. The bug was narrower: this one Product-B-owned demo *customer* login should never have held that role. Fixed via `backend/sql/fix-alex-rivera-safety-team-role.sql` (bundled into the migration named above), directly authorized by the product owner on 2026-09-04, and **confirmed live** — a fresh query against `auth.users` shows the role is now `NULL`.
- `create_booking_with_schedule` (see `backend/schema.sql`) locks and checks a listing's slot before creating a booking, so two customers racing for the identical time slot can no longer both succeed — one gets a clear "no longer available" error instead of a silent double-booking. Proven with a real, timed two-session concurrency test against an isolated database (Session A holds the slot briefly, Session B blocks, then correctly fails once A commits) before applying it here. A second function, `get_booked_slots`, now also closes the UI-level half of this: the listing-detail page fetches already-taken slots for that listing and hides them, so a second customer can no longer even be *offered* a slot someone already holds, not just blocked from completing it — no longer an open gap either.
- `fetchListings()`'s `search` filter is now applied server-side via a `.or()` `ilike` filter (`frontend/js/api.js`), backed by `pg_trgm` GIN indexes on `listings.title`/`description` (`backend/schema.sql`) — no longer a client-side scan. What's still unbounded: `fetchListings()` has no `.range()`/page size, so it fetches and renders every matching row in one call. Harmless at today's ~100 seeded listings; would need pagination before a much larger catalog.
- `booking_schedules` and the removal of `chatbot_requests.customer_id` — both now confirmed with the team (Joan signed off on `booking_schedules`; Lady D signed off, for now, on dropping the column) and reflected in the shared database's actual schema. What's still open: Product C (Matching Chatbot) hasn't shared a repo with the team, so whether its code has been updated to match — as opposed to just the schema decision being verbally agreed — is unconfirmed.
- `vercel.json`'s Content-Security-Policy has been confirmed live (response headers checked, and the full login → browse → book → My Bookings flow walked end-to-end with zero console errors on the deployed URL), but only by manual review and a single pass through the core flow — not a `Content-Security-Policy-Report-Only` run against varied real traffic.
- `vercel.json` uses the raw `routes` array, not the `cleanUrls`/`rewrites` convenience config it used before. Root cause of the outage below: `rewrites` always compiles to a `check: true` rewrite, which re-runs the *entire* route table against the rewritten path — for `/` rewritten to `/index.html`, that re-triggered the clean-URL-normalizing redirect rule (which also matches `index.html`), producing a self-redirect (`Location: /`) that Vercel resolves as a 404 rather than looping forever. Confirmed by inspecting the generated `.vercel/output/config.json` and reproducing the exact broken response against an isolated preview deployment. Switching to raw `routes` meant manually replacing what `cleanUrls` used to auto-generate — explicit rewrites for `/login`, `/listings`, `/listing`, `/bookings` alongside `/` — since raw `routes` doesn't get the automatic file-override mapping `cleanUrls` provides. All of it (every page, both clean and `.html` forms, `sw.js`, `manifest.json`, static assets, a genuine 404 case) verified against an isolated preview deployment via `vercel curl`'s automatic deployment-protection bypass before this was ever considered safe to reintroduce to `--prod`.
- `.github/workflows/test.yml` has a `deploy` job (`needs: test`) that deploys straight to **production**, gated on the test job passing first — read the comment directly above that job in the workflow file before changing that. A first attempt at this used `--prod` directly and broke the live site: `vercel build` + `vercel deploy --prebuilt` (the officially documented CI deploy pattern) generates a different routing config than Vercel's own managed build pipeline, and that difference 404'd the root path (`/`) for real visitors for several minutes — restored at the time by reverting to a direct `vercel --prod` deploy, not by understanding the actual cause. The cause above is now understood and fixed, verified against three separate rounds of routing/header bugs (see `scripts/smoke-test-deployment.sh` below), and the job ran clean as `deploy-preview` (preview-only) across a long run of real pushes before deliberately flipping it to `--prod`. It carries a `concurrency` group (`production-deploy`, `cancel-in-progress: true`) so a newer push cancels an older push's still-running deploy instead of racing it for the production alias. Deploy and promote are deliberately two separate steps (`vercel deploy --prod --skip-domain`, then a later `vercel promote` only if the smoke test passes) rather than `--prod` alone aliasing the domain immediately — that ordering means neither a smoke-test failure nor a `cancel-in-progress` cancellation can ever leave unverified code live; the production domain simply isn't touched until verification has actually finished and passed. Vercel's own Git-integration auto-deploy is disabled (Settings → Git → Ignored Build Step is set to the "Don't build anything" / `exit 0` command, confirmed live 2026-09-03) — see the note in "Deploy to Vercel" below; this job is the only path to production.
- `scripts/smoke-test-deployment.sh` runs after every preview deploy in CI (via `vercel curl`'s deployment-protection bypass, so it works without a browser session). It exists because three consecutive rounds of `vercel.json` bugs — root path 404ing, trailing slashes 404ing, redirects missing security headers — were each only caught by manually re-running the same handful of checks by hand; none of it was a repeatable test until now. Verified against both the current (fixed) config and the original broken one, to confirm it actually fails when it's supposed to, not just that it passes today.
- Vercel doesn't auto-prune deployments, and `deploy` creates a new one on every push to `main` — 31 had piled up (almost entirely superseded) before anyone noticed, back when the job was still called `deploy-preview`. `scripts/cleanup-deployments.sh` removes every deployment for this project except whichever one currently holds the production alias (`--safe`, so the live site is never at risk regardless of when this runs). Not on a schedule — run it occasionally by hand.
- If production ever needs to go back to a previous deployment — a real problem that only shows up in front of real traffic, after the deploy job's own smoke test already passed — `scripts/rollback-production.sh` wraps `vercel rollback`: run it with no arguments to list recent production deployments, then again with one of those URLs to actually roll back, which re-runs `smoke-test-deployment.sh` against the live production domain afterward to confirm it took and is healthy. No rollback procedure existed anywhere in this project before this; it went unaddressed across several review rounds despite being flagged as a real gap each time.

## Getting started — step by step

### 1. Run it locally right now (no setup required)

The app ships with a **local demo mode**: if no Supabase project is configured, it automatically reads from the JSON files in `frontend/data/` and stores bookings in your browser's `localStorage`. This is the fastest way to see it working.

```bash
python3 scripts/dev-server.py
```

Open `http://localhost:8901` in a browser, and log in with one of the four demo buttons on the login screen (Alex / Jordan / Morgan / Taylor — click a name to auto-fill the email and password). This is a thin wrapper around `python3 -m http.server` that adds `Cache-Control: no-store` to every response — plain `http.server` sends no cache headers at all, so the browser is free to keep serving a pre-edit version of a file after you've changed it and reloaded, with nothing indicating that's what happened. (Pass a port number to use something other than 8901.)

### 2. Set up the real backend (Supabase) — optional, not needed for the current presentation

1. Create a free project at [supabase.com](https://supabase.com).
2. In the Supabase dashboard, open the **SQL Editor** and run, in order: `backend/schema.sql`, then `backend/seed_data.sql`, then `backend/seed_demo_bookings.sql` (gives the 4 demo accounts a mix of pending/confirmed/completed bookings to click through instead of an empty screen).
3. In **Project Settings → API**, copy your Project URL and `anon` `public` key.
4. Paste them into `frontend/js/config.js`:
   ```js
   window.APP_CONFIG = {
     SUPABASE_URL: "https://your-project-ref.supabase.co",
     SUPABASE_ANON_KEY: "your-anon-key",
   };
   ```
5. Create the four demo sign-ins in Supabase Auth:
   ```bash
   cd backend
   npm install
   SUPABASE_URL=https://your-project-ref.supabase.co \
   SUPABASE_SERVICE_ROLE_KEY=your-service-role-key \
   npm run seed:users
   ```
   (Find the service role key in the same Project Settings → API page — never put it in `frontend/`.)

Reload the frontend and it will now talk to your real Supabase database instead of the local JSON fallback.

### 3. Deploy to Vercel

Already done — see the live demo link at the top of this README, and this repo is Git-connected to that Vercel project. **A push to `main` deploys it automatically, but only through `.github/workflows/test.yml`'s CI-gated `deploy` job** — don't also run `vercel --prod` by hand after pushing; that creates a second, redundant production deployment for the same commit instead of doing anything useful. (Found out the hard way: several rounds of this project's history did exactly that.)

**Only one thing deploys to production on a push.** Vercel's own Git-integration auto-deploy — which would otherwise react to the same `git push` with no awareness of the CI run at all — is disabled: the project's **Settings → Git → Ignored Build Step** is set to the "Don't build anything" (`exit 0`) command, confirmed live in the dashboard. An earlier version of this README assumed that setting was still the default (enabled) and listed disabling it as an open gap — it wasn't; the dashboard had already been configured correctly, that just hadn't been checked against what this doc claimed. `.github/workflows/test.yml`'s `deploy` job (gated on `test` passing first) is genuinely the only path to production.

(From a fresh clone: push this repo to GitHub, then in Vercel "Add New Project" → import it — `vercel.json` already points Vercel at the `frontend/` folder, so no extra config is needed. That one-time setup is what wires up the auto-deploy-on-push behavior described above.)

### 4. Run the automated tests

There are three tiers, deliberately not one — see each tier's own header comment for the full reasoning:

**Tier 1 — the default suite, safe on every push, no real database needed.**
```bash
cd frontend && npm install && cd ..
node --test --experimental-test-coverage frontend/js/*.test.mjs
```
138 tests: every page module's DOM behavior (both app modes, now including `page-signup.js`), `filterListings`/`formatCurrency`/etc.'s pure logic, `signUp()`'s mock-mode parity and real-mode Supabase Auth error-code translation, WCAG contrast, axe-core structural accessibility, data-integrity invariants across all six seed-data files, CI/config hygiene checks (every workflow action SHA-pinned, permissions minimal, `dependabot.yml` present), and `error-reporter.js`'s error/rejection capture. `npm install` is only needed once, for `jsdom`, `axe-core`, and `@playwright/test` (tier 3, below) — `frontend/`'s only dependencies, all dev-only, never shipped to the deployed app. `--experimental-test-coverage` is Node's own built-in flag. Its numbers are trustworthy for every file except `page-index.js`/`page-login.js`/`page-listing.js`/`page-listings.js`/`error-reporter.js` — their own tests import their entry module with a fresh cache-busting query string per test (see those files' own comments for why), which breaks coverage *attribution* specifically: V8 only reports the last-loaded instance's counters, understating what's actually tested.

**Tier 2 — live-database checks, run by hand (or on a schedule), not on every push.**
```bash
node --test frontend/js/live/rls-policies.test.mjs   # 12 tests: RLS, triggers, and grants, against the real Supabase project
node --test frontend/js/live/concurrency.test.mjs    # 4 tests: the double-booking race lock, proven with genuinely concurrent requests
node --test frontend/js/live/known-issues.test.mjs   # 1 test: a deliberate, currently-failing regression test — see below
```
This is the one place anything checks that `backend/schema.sql`'s RLS policies, triggers, and grants actually enforce what they claim — real HTTP calls against the real, shared project, using the 4 real demo accounts. Not part of Tier 1 on purpose: running this on every push would hammer the team's shared project and create real side effects (a couple of these tests write a real row — see `backend/scripts/cleanup-live-test-data.mjs`) on a schedule nobody chose. `known-issues.test.mjs` holds one deliberate, currently-failing `KNOWN LIVE ISSUE` test — see its own comment for what it's flagging and why it's left failing rather than worked around — split into its own file so `.github/workflows/live-tests.yml`'s scheduled run doesn't show the whole job as failed every single time over one known, already-tracked issue; that workflow runs it as a separate `continue-on-error: true` step instead.

**Tier 3 — real-browser end-to-end, visual, and performance-budget checks.**
```bash
cd frontend && npx playwright install chromium webkit && npm run test:e2e
```
34 tests (across `desktop-light`/`desktop-dark`/`mobile-light`/`throttled-mobile`) drive an actual browser against the app running on `scripts/dev-server.py`, talking to the real Supabase project — login, search, filters, pagination, the full booking flow (a real booking is created and left in place; same cleanup script as Tier 2), rating, three screenshots per page per theme/viewport, page-weight/load-time budgets, and one real Slow-4G-throttled load (Chromium CDP network emulation — see `e2e/performance-throttled.spec.mjs`). Two of the 34 (the real booking flow and the rating flow) skip cleanly rather than fail if no open slot/unrated booking currently exists in the live demo data — a dynamic, self-documenting skip, not a bug; running the full suite repeatedly in one sitting can exhaust that state faster than anyone's replenishing it by hand. `playwright.config.mjs` pins `workers: 1` — Supabase Auth rate-limits sign-ins per IP, and running this suite's many logins in parallel across projects hit that limit in practice, not just in theory; a single, isolated login test can also flake from cumulative sign-ins across an earlier full run in the same session — rerun it alone to confirm before treating it as a real regression. `.github/workflows/performance.yml` runs `performance.spec.mjs`/`performance-throttled.spec.mjs` weekly (plus manual dispatch), uploading the measured page-weight/load-time/FCP numbers as a build artifact so a slow creep is visible over time, not just a hard budget breach.

Together, Tiers 1–3 total roughly 187 automated tests. None of Tiers 2–3 run in `.github/workflows/test.yml` on every push (see that file's own comments) — CI stays fast and deterministic; the live/browser tiers are for a deliberate, occasional, human-triggered (or, for performance, weekly-scheduled) check.

### 5. Testing checklist before you call it done

- [ ] Log in with each of the 4 demo accounts.
- [ ] Sign up as a brand-new account and confirm it can actually book something (i.e. it has a working `customer_profiles` row, not just an `auth.users` row) — the provisioning migration is live as of 2026-09-04.
- [ ] Browse listings; filter by service type, search text, and max price.
- [ ] Open a listing, pick a time slot, and book it — confirm it shows up under "My Bookings" with the correct scheduled time.
- [ ] Confirm a completed booking can be rated 1–5 and the rating persists.
- [ ] Log out and confirm you're redirected to the login screen, and that visiting `listings.html` directly while logged out redirects you back to login.
- [ ] Resize the browser to a phone width and confirm the layout still reads cleanly.
- [ ] Switch your OS/browser to dark mode and confirm text stays readable (status pills, badges, buttons all have dark-mode colors defined in `frontend/css/styles.css`), and — on a supported mobile browser — that the address bar/status bar tints to match.
- [ ] Open DevTools → Application → Service Workers and confirm `sw.js` shows as activated, then reload with the network throttled to "Offline" and confirm the app shell still loads. (Claude Code's own sandboxed preview can't register service workers at all — this needs a real browser tab.)
- [ ] Log out, then click the browser's Back button: confirm you land on (or stay on) the login screen rather than briefly seeing a previous page's real data.
- [ ] (Real Supabase mode only) As a signed-in customer, try updating a booking's `total_cost` or `booking_status` via a direct `supabase.from('bookings').update(...)` call in the browser console — it should be rejected by `bookings_protect_update`.
